# Outcome

AutoCode loads the canonical ordered workbook, validates its task graph and declared state against materialized and completed task records, deterministically selects the single next legal task, and gives one workbook run durable exclusive ownership that can be safely reconciled after interruption.

## Why now

AC-015 established provider-neutral role execution. Before the complete task kernel can be dogfooded on AC-017, the runtime must stop inferring order from task filenames and must prevent two invocations from executing the same canonical task.

## Required context

- `tasks/README.md` — canonical MVP 1 order, state rules, and JIT materialization process.
- `docs/PRODUCT.md` — M1-01, M1-03, repository lifecycle boundary, and non-goals.
- `docs/ARCHITECTURE.md` — workbook/scheduler/ownership boundaries and durable-state invariants.
- `docs/WORKFLOW.md` — eligibility, repository handoff, evidence, and resume rules.
- `docs/SECURITY.md` — untrusted repository input, path safety, protected state, and interruption rules.
- `SYSTEM.md` — verified current implementation and limitations.

## Scope

### In

- A bounded parser for the canonical MVP 1 sequence in `tasks/README.md` with exact ordered task identity, declared workbook state, dependency/state consistency, and duplicate/cycle validation.
- Eligibility derived from workbook order, task contracts, completed records, and predecessor repository presence; malformed or contradictory inputs fail before runner or durable task effects.
- A versioned, atomic durable ownership record bound to workbook content, selected task content, Git identity, worktree, and a stable workbook-run identity.
- Exclusive single-task acquisition, same-run resume, stale/dead owner reconciliation, and conservative blocking when ownership is live, changed, corrupt, or ambiguous.
- Integration of canonical selection/ownership at the workflow intake boundary and deterministic CLI/test coverage.

### Out

- Executing more than one task kernel per invocation, automatic canonical state edits, moving task files, immutable final summaries, or successor continuation (AC-018).
- Required CLI QA recovery and unifying QA findings with the fix loop (AC-017).
- Remote PR/merge/deploy automation, authenticated live-model compatibility, or additional operating-system acceptance.
- A second workbook/state database, parallel task execution, hosted coordination, or automatic creation of future task contracts.

## Implementation constraints

- `tasks/README.md` remains the only manual sequencing/state authority; runtime state may cache bindings and ownership but must not become a second task board.
- Parse only a strict, bounded canonical table/section and reject ambiguity; do not accept arbitrary Markdown as execution authority.
- A PR-required predecessor is complete only when its completed record and current target-branch ancestry support the workbook's `done` state. Local handoff alone cannot unlock dependents.
- Ownership must be append/publish safe, path-contained under `.autocode`, bound to current inputs, and recoverable without stealing from a live or ambiguous owner.
- Preserve the existing role/runner containment boundary. Workbook text and task content are untrusted data and cannot grant capabilities or select commands.
- Reuse the repository's durable lock, identity, bounded-read, and atomic-publication patterns where practical; add no external dependency unless unavoidable.
- Implement only from `feat/AC-016-workbook-ownership` in its isolated worktree.
