# Outcome

An operator can configure the planner, implementer, reviewer, and fixer as role assignments to a validated runner and optional model, while the existing Codex CLI behavior remains available as the first supported adapter. The workflow depends on provider-neutral role results and capabilities rather than branching on Codex-specific concepts.

## Why now

The reconciled MVP 1 workbook requires a stable execution contract before durable workbook scheduling is added. Current code hard-codes role names, Codex process options, prompts, session records, and workflow calls in `codex.ts` and `workflow.ts`; building scheduling first would spread that coupling into the workbook engine.

## Required context

- `tasks/README.md` — canonical MVP 1 order and historical reconciliation.
- `docs/PRODUCT.md` — M1-02 and non-goals.
- `docs/ARCHITECTURE.md` — role, runner, model, adapter, and evidence boundaries.
- `docs/WORKFLOW.md` — role semantics and current one-task execution.
- `docs/SECURITY.md` — subprocess containment, untrusted output, credentials, and evidence controls.
- `SYSTEM.md` — verified current implementation and limitations.

## Scope

### In

- A versioned configuration schema for the required `planner`, `implementer`, `reviewer`, and `fixer` assignments.
- A provider-neutral runner interface covering preflight, invocation, bounded result/evidence, capabilities, and stable effect identity.
- A Codex CLI adapter that preserves current containment, redaction, fresh-session behavior, and role-specific write/read-only authority.
- Workflow resolution through configured roles without Codex-specific branching in the orchestration layer.
- Deterministic tests for defaults, explicit model selection, invalid/unknown assignments, capability mismatch, distinct independent review, receipt freshness, and resume.

### Out

- A second production runner/provider, direct model-provider APIs, hosted execution, parallel roles/tasks, workbook scheduling, task ownership, QA recovery, remote PR/merge/deploy automation, and release packaging.
- Changing the accepted conservative behavior for ambiguous effects or unsupported platforms.

## Implementation constraints

- Role is workflow responsibility, runner is the executable adapter, and model is an optional runner-specific selection; do not conflate them.
- Configuration and evidence may retain runner/model identifiers but never credentials or an inherited secret-bearing environment.
- The reviewer remains independent from the implementation effect and read-only; capability mismatches fail before model or durable effects.
- Preserve the current Codex CLI defaults for existing valid projects or provide an explicit, tested migration with no silent behavior change.
- Keep adapter-specific prompts/process parsing inside the adapter boundary. Core workflow results must be bounded, validated, immutable, and backend-neutral.
- Work only from `feat/AC-015-configurable-role-runners` in an isolated worktree created from current `main`.
